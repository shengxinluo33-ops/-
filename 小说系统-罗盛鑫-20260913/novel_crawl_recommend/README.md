# 爬虫驱动小说检索推荐系统

输入一个小说类型（武侠 / 言情 / 科幻…）或者一句描述（"女主重生复仇古言"），
返回带排名、评分、书名、作者、简介、来源链接的榜单。
**也可以直接说人话**——"我想看无脑爽文男主厉害"，`/api/agent` 会先理解你要什么
再推荐（见下面「AI 推荐」一节）。

采集走 Tavily 搜索 + requests/bs4 静态解析 + Playwright 动态渲染，
元数据进 SQLite，简介做 embedding 进 FAISS，三种检索模式，Web 页面在 **5001**。

三个数据来源，层次不同：

| 来源 | 拿到什么 | 说明 |
|---|---|---|
| 公开榜单页（Tavily 搜索 + 抓取） | 书名、作者、简介、来源链接 | `crawler.py`，早期的主力来源 |
| **起点中文网**移动端 | 上面那些 + **封面图** + 起点自有分类 | `qidian_source.py`，只取元数据，上限 ~75 本 |
| **微信读书** weread.qq.com | 补出版书/经典的**封面**，以及**评分（推荐值）** | `weread_source.py`，只在缺封面/缺评分时按书名查一次 |
| **中国国家图书馆** nlc.cn | 一条权威链接 | `nlc_source.py`，尽力而为，搜不到就留空 |

**当前库规模：8062 本，22 个分类**，向量索引 8062 条 / 1024 维 / BAAI/bge-m3。

采集分**两条路**，都是我们组自己爬的：

1. **榜单页抓取**：Tavily 搜索拿到榜单页 URL → 校验 robots.txt → requests/bs4 静态解析
   → 正文不足 120 字才降级 Playwright 渲染 → 直接进主库。
2. **协作库那批**：负责数据库的同学爬完打包上传到 **GitHub 协作库**
   （原始 7970 行：起点 3950、红袖添香 3774、豆瓣读书 193、小说阅读网 53），
   再由我们用 `import_csv.py` 合并进主库。

两路合完整体去重，最终入库 **8062 本**
（去重按 `UNIQUE(title, category)`，重采到同一本是更新，不是堆量）。
起点中文网 / 微信读书 / 国家图书馆三路是在这之后**回填**封面、评分和权威链接的。

站点分布（`source_site` 直查）：红袖添香 3734、起点中文网 3672、
起点中文网（封面回填）231、豆瓣读书 190、微信读书（封面回填）152、
小说阅读网 53、未标 30。

协作库那批数据作者字段完整（7987 本有作者）、简介平均 137 字，
但**没有封面 URL、97.6% 没有评分**（`rating` 全是 0.0，导入时按缺失处理）。

**关于评分（311 本有真实评分）**：豆瓣那批自带 190 本，其余 121 本是脚本回填补的
（起点 77 本、微信读书 26 本、红袖 16 本、未标 2 本）。剩下 7751 本没有评分，
页面显示" — "——0.0 存的是「没抓到」，不是「打了 0 分」。

**关于封面覆盖率（8062 本里 470 本有真封面，5.8%）**：
383 张是脚本回填的（起点 231 + 微信读书 152），87 张是采集时自带的。

## AI 推荐：说人话就能搜

搜索框左边的检索方式里多了「AI 推荐（说人话）」，**默认就是这个**。
输入"我想看无脑爽文男主厉害"，模型先把这句话翻成检索条件，再交给现有检索。

```bash
python intent.py "我想看无脑爽文男主厉害"   # 命令行直接试
```

**为什么 agent 只做"翻译"，不做多步规划**：实测这个模型（`agnes-2.5-flash`）
一次结构化输出要 **0.35~20 秒**，自由生成 4.7 秒。让它自己决定查几次库、
或者给 20 本书各写一句推荐理由，页面就没法用了。所以它只吐一个 JSON：

```json
{"category":"玄幻","keywords":["无敌","爽文"],
 "intent_echo":"想看男主无敌的爽文","relevant":true}
```

**检索走哪条路，取决于模型给没给关键词**（这是实测出来的，不是拍脑袋）：

| 模型返回 | 走哪条路 | 实测 |
|---|---|---|
| 有分类 + 有关键词 | `分类 AND 关键词` | 「无脑爽文男主厉害」→ 玄幻+无敌 → **30 本**，靠谱 |
| 有分类 + 没关键词 | 语义检索 | 「睡前轻松小甜饼」只给分类等于整个言情 **978 本**，没筛；语义能给出《吾家阿囡》《校草大人微微甜》 |
| 没分类 + 有关键词 | 关键词检索 | — |
| 两个都没有，但没说无关 | 语义检索 | 模型保守起来会什么都不给，不该跟着放弃 |
| `relevant: false` | **不检索** | 「今天天气怎么样」→ 结果区直接说明"这与小说无关"，不硬凑 |

（第一行为什么不能走语义：试过，语义会命中"帅""无敌"这些字面，给出
《天灾囤亿万物资，我刷爆了渣男卡》《无敌帅夫君》这种，反而不如关键词准。）

**候选词会依次降级**：模型给 1-3 个候选，按"最具体 → 最泛"排列，后端从
第一个开始试，命中不足 5 本就退到下一个。`LIKE '%无脑爽文%'` 只有 **1 本**，
而 `LIKE '%爽文%'` 有 **131 本**——不降级的话用户搜"无脑爽文"会以为系统坏了。

**带分隔符的关键词按片段 OR 匹配**：搜「无脑 爽文」= 匹配含"无脑"**或**
"爽文"的，实测 146 本。原来直接拼成 `LIKE '%无脑 爽文%'`，等于要求原文里
正好有个空格，搜不到东西。**没加分隔符的仍当整体匹配**，不擅自切词——
否则「张三丰」会被切成「张三」「三丰」误伤一片。详见 fixlog 第 26 条。

**四级降级，任何一层都不白屏**：

1. 没配 `API_KEY` / 超时 8 秒 / 返回非法 JSON → 退回**规则匹配**
   （在分类表里做包含匹配），前端会写明"AI 没接住，按规则匹配：…"
2. 分类+关键词查出 0 条 → 退纯分类
3. 还是 0 条 → 兜底语义检索
4. 前端 12 秒没等到 → 提示后自动改走语义检索

新增的环境变量（不填也能跑，只是没有 AI 那层）：

```
API_KEY / BASE_URL / MODEL_ID   聊天模型，意图解析用
INTENT_TIMEOUT                  默认 8 秒
```

207 → 198 这一步是**删噪声**：《纽约时报》《紐約時報》《华尔街日报》《柯克斯书评》
《时代》《時代》《今古传奇》是媒体名/杂志名，《刘慈欣》《风凌天下》是作者名，
《新书》是榜单页导航词——它们是榜单页写"入选《纽约时报》年度好书"时，
被《》正则当成书名摘进来的，不是书。规则见 `crawler.noise_reason()`，
删之前会先把判定原因逐条打印出来。

一开始只有 37%，瓶颈不是缺源而是**起点搜索取错了书**——它取页面里第一个
`/book/{id}`，不核书名，于是既可能配错封面，又每条都白搭一次详情页请求
（134 本 = 268 次请求，直接把自己跑到 403）。
改成"先解出书名、核上了再取，且搜索页自带封面就不再抓详情页"之后，
请求量减半，一次跑完 128 本拿到 62 本，全程 0 次 403。细节见 `logs/fixlog.md` 第 16 条。

剩下 26 本没封面。上次卡住的两类现在已经能处理：繁体书名（紐約時報、狼廳、
荒野偵探、地下鐵道）靠 `titlematch` 的繁简归一化对上了，系列分册
（法医秦明：天谴者/遗忘者/玩偶…）也不再被冒号规则拦。
剩下的是真·冷门网文（非赢游戏、洛阳农牧事…）和几本外文原著，
起点和微信读书都没有，占位封面兜底即可。逐类分析见 `logs/fixlog.md`。

**请求配额有限，别硬闯**：起点被限流过两次，都是几百次请求堆出来的。
代码里有熔断（403 立刻停手），跑大批量前用
`CRAWL_MIN_DELAY=2 CRAWL_MAX_DELAY=4 python qidian_source.py backfill` 降速。

没有真封面的书用**书脊样式占位封面**（按书名哈希选稳定色相 + 渐变底 +
书名/作者/分类文字 + 装订线），看着是设计过的，不像缺失。
真封面盖在占位之上，图片挂了会自然露出占位，不需要 onerror 兜底。

> **只采元数据，不采章节正文。** 起点等平台上的连载小说受版权保护，
> 批量下载正文入库是侵权，本项目**不做**这件事（自测里有断言卡这条底线）。
> 公版书（四大名著、鲁迅等已进入公有领域的作品）的全文对接是另一回事，
> 当前环境的维基文库不可达，暂未实现。

## 4.8 导出 novels.csv 给前端

```bash
python export_csv.py            # 导出，噪声条目只扫描不删
python export_csv.py --clean    # 先删噪声条目再导出（删完自动重建向量索引）
```

格式按课程 `KUST/ch2-rag/notebooks/database.txt` 的约定：文件名 `novels.csv`、
UTF-8、英文逗号、第一行英文表头 `title,author,category,rating,description,url`。
简介里有逗号和引号，所以走 `csv` 模块转义，别手写 join。

**导出只改 CSV，不动数据库**——库里始终存的是抓到的原始值。两处加工：

- **噪声条目**：媒体名/杂志名/作者名/导航词，规则见 `crawler.noise_reason()`。
  加 `--clean` 才删，默认先把清单和判定原因逐条打出来给人核一眼。
- **rating**：约九成的书抓不到评分，按**同分类均值**填占位值，且只采纳 ≥5 分的
  真实评分来算均值（页面上的无关数字会被正则误抓成 1.0，
  拿它算均值会让整个分类都被拉到 1.0）。

给前端的数据说明写在 `novels_dataset_README.md`，跟 CSV 一起交付。

## 4.9 数据维护：清洗简介 + 合并重复条目

```bash
python clean_data.py            # dry-run：只打印会改什么
python clean_data.py --apply    # 真改库，最后自动重建向量索引
```

采集来的简介有三类脏，都不是广告，原来的 `clean_text` 拦不住：

1. **百科页面的目录结构**：`## 目录 ## 创作背景 ### 文学来源`，格式像简介、内容什么都没说。
2. **自媒体模板**：`📖【书名】💡【作者】🍃【出版社】`，删掉【标签】留下来的才是正文。
3. **页面外壳**：导航条（"阅读记录 五二首页 最近更新 言情书单…"）、
   商店信息（"sur Apple Books … 7,49 €"）、邮箱、emoji。

清洗完仍然没内容的（<12 字、百科目录、导航/商店残留）用
"《XX》是XX创作的XX类小说" 兜底。

**阈值和采集时不一样**：采集时用 40 字兜底，这里用 12 字。很多真实简介本来就短
（《捞尸人》"人知鬼恐怖，鬼晓人心毒。这是一本传统灵异小说。"才 23 字），
拿 40 字卡它们等于把真数据换成模板句。

重复条目是同一本书的不同译名/原题，自动检测靠 `titlematch.normalize()` 归一化后分组，
中外文异名（`狼廳` / `Wolf Hall`）对不上，走 `KNOWN_DUPES` 手工清单。
每组保留信息最全的那条（封面 > 评分 > 作者 > 简介长度），缺的字段从另一条补过来再删。

**清洗和去重会重建向量索引**（简介变了向量得重算，条目删了索引里就多一条孤儿），
所以两件事放在一个脚本里，只重建一次。

## 4.10 合并协作库那批（`import_csv.py`）

```bash
python import_csv.py                        # dry-run：只统计不写库
python import_csv.py --apply                # 真写库
python import_csv.py --apply --reindex      # 写完顺带重建索引
python import_csv.py --src /path/to/x.csv   # 换文件（默认 novels (1).csv）
```

和 `export_csv.py` 是反方向。合并语义靠 `save_novels` 的 `ON CONFLICT` 实现，
**按 `(title, category)` 判重，重复是更新不是堆积**：已有封面和评分不会被空值盖掉，
简介取更长的那条。所以协作库那批数据不会把我们采到的封面和真实评分冲掉。

**`rating = 0.0` 一律当缺失**。这是最关键的一条：协作库那批数据 97.6% 的评分都是 0.0，
那是"没抓到"不是"打了 0 分"。真当 0 分存进去，现有的 118 个真实评分会被淹没在
一片 0.0 里，按评分排序就彻底失效了。

**写完要重建索引**，否则新书没有向量、语义检索查不到它们（`--reindex`）。
八千条 embedding 是**分批**发的（`store.EMBED_BATCH = 128`）：
一次把八千条全塞进请求会直接超服务的 token 上限，分 63 批约 34 秒跑完。

## 4.11 分类归一（`normalize_categories.py`）

```bash
python normalize_categories.py            # dry-run：打印映射表
python normalize_categories.py --apply    # 真改库
```

协作库那批数据 带了 54 个分类，里面两类脏，各用一条规则处理：

1. **同类异名按关键词合并**（`CATEGORY_RULES`，**按顺序匹配，先匹配到的生效**）：
   悬疑 / 悬疑灵异 / 悬疑侦探 / 悬疑推理 / 推理 → **悬疑**；
   古代言情 / 现代言情 / 玄幻言情 / 言情 → **言情**；
   科幻 / 科幻空间 → 科幻；仙侠 / 仙侠奇缘 → 仙侠；游戏 / 游戏竞技 → 游戏；
   浪漫青春 / 青春 / 青春文学 → 青春；体育 / 体育运动 → 体育；现实 / 现实生活 → 现实。

   顺序有意义：**"玄幻言情"同时含"玄幻"和"言情"，它在红袖是言情频道
   （玄幻背景的言情），所以言情规则排在玄幻前面。**

2. **不是小说分类的归到"其他"**（`NON_FICTION`）：计算机网络、管理、经济、法律、
   医学、宗教、投资理财、期刊杂志、文学、文化、童书……这些是豆瓣的**图书**分类，
   混在小说库里很怪。还有"小说"这种等于没分类的宽泛标签。

**归一后有同名的书会撞 `(title, category)` 唯一键**——《江湖》在"小说"和"文化"
里各有一条，归并到"其他"就重了。脚本会先合并这些冲突组（保留信息最全的一条，
缺的字段从另一条补过来），**删了行才需要重建索引**；没删行就只改字段，
索引不用动（FAISS 存的是 `novels.id`，简介向量也没变）。

54 个分类 → **22 个**，前几名是：言情 978、轻小说 717、都市 687、科幻 626、
仙侠 604、历史 582、悬疑 524、游戏 521、玄幻 490。

需要的环境变量（读项目根目录的 `.env`）：

| 变量 | 用途 | 不填会怎样 |
|---|---|---|
| `TAVILY_API_KEY` | 搜分类榜单 | 采集直接报缺少 Key |
| `EMBEDDING_API_KEY` | 简介向量化 | 降级成本地哈希向量（只能抓字面重合） |

## 2. 数据表 schema

SQLite 库在 `data/novel.db`，表名 `novels`：

```sql
CREATE TABLE novels (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    title       TEXT    NOT NULL,      -- 书名
    author      TEXT    DEFAULT '',    -- 作者
    category    TEXT    NOT NULL,      -- 分类
    score       REAL,                  -- 评分，抓不到就是 NULL，页面显示" — "
    rank_num    INTEGER,               -- 榜单排名，按采集顺序从 1 编
    description TEXT    DEFAULT '',    -- 简介
    source_url  TEXT    DEFAULT '',    -- 来源网页链接
    create_time TEXT    DEFAULT (datetime('now','localtime')),
    UNIQUE(title, category),           -- 重复采集同一本是更新，不是堆积

    -- 后加的四个字段（老库启动时自动 ALTER 补上）
    cover_url      TEXT DEFAULT '',    -- 封面图，只有起点来源有
    site_category  TEXT DEFAULT '',    -- 来源站自己的分类（如"东方玄幻"）
    source_site    TEXT DEFAULT '',    -- 起点中文网 / 榜单页解析
    catalog_url    TEXT DEFAULT ''     -- 国图 nlc.cn 上的相关页，搜不到就空着
);
```

`UNIQUE(title, category)` 是有意的：再采一次「武侠」会把已有记录更新掉
（简介取更长的那条、封面/国图链接保留已有值，不覆盖成空），而不是把库撑大。

向量库在 `data/novels.faiss`，`data/novels_faiss_meta.json` 里存
**每条向量对应的 novels.id**、维度和模型名。用 `IndexFlatIP`，
向量做过归一化，所以内积就是余弦相似度。

## 3. 两种查询怎么用

**模式① 分类/关键词检索** —— 我知道想看哪一类。

```bash
python recommender.py keyword 武侠
```
从 SQLite 按 `category` 筛，可按评分降序或榜单排名升序。
输入不在预设分类里时，退化成书名/作者/简介的模糊匹配。

**模式② 语义检索** —— 我说不清分类，但说得出想看什么。

```bash
python recommender.py semantic 江湖恩怨 刀光剑影
```
把查询和简介都做成向量，用 FAISS 找最像的几本，返回相似度。
**这是关键词检索做不到的**：搜"刀光剑影"能召回简介里没这四个字但讲武林争斗的书。

页面上用单选按钮切两种模式，`/api/query?mode=...` 是同一个入口。

## 4. Web 页面

```
GET  /                 页面
GET  /api/query        ?q=&mode=keyword|semantic&sort=score|rank&limit=&page=
GET  /api/categories   库里有哪些分类、各多少本（导航栏靠它动态生成）
POST /api/crawl        {"category":"言情","limit":6}     采公开榜单页
POST /api/crawl_qidian {"limit":10,"category":""}        采起点榜单（只元数据）
GET  /api/status       库里多少条、索引多少维、什么模型
```

**分页**：`limit` 每页条数（默认 20，上限 60），`page` 从 1 开始。
响应里带 `total`（符合条件总共多少本）和 `has_more`，前端靠这两个翻页。
库涨到八千本之后一页装不下，不分页浏览器会直接卡死。
语义检索不走分页——FAISS 一次就把最像的 N 本给完了。

**分类是动态的**（`GET /api/categories`），不是写死的：库里有 54 个分类，
导航栏默认摊开 10 个热门的（带本数），其余收进"更多"。
分类查询走的是 `category LIKE`，所以查"言情"能同时命中
"古代言情""现代言情""玄幻言情"，查"三体"则自动落到关键词检索去书名里搜。

页面分两块视图，右上角切换：

- **封面卡片**：竖版封面网格，卡片上有 TOP 角标、分类标签、相似度/来源站点；
  没有封面时用书名首字 + 稳定色相生成占位封面（同一本书颜色不变）；
  点卡片开详情抽屉——大封面、完整简介、评分星级、来源链接、国图链接、入库信息。
- **榜单表格**：排名｜评分｜书名｜作者｜简介｜来源链接（语义模式多一列相似度），
  前三名排名标红。这是任务书要求的那一版。

顶部搜索框 + 分类导航栏（全部/武侠/玄幻/都市/言情/科幻/悬疑/历史），
右上角「采起点榜单」「采分类」两个按钮可以在线扩库。

## 4.2 长期在线：关掉终端也一直在，别的电脑也能开

端口 **5001**。直接 `python app.py` 起的进程，关掉终端/关掉 AI 会话就没了，
所以要交给 `start_web.sh` 托管：

```bash

./webctl.sh status          # 看在不在跑、库里多少本
./webctl.sh restart         # 改完代码重启
./webctl.sh stop            # 停掉
./webctl.sh log             # 跟日志
```

三件事叠起来才能保证"随时随地打得开"：

1. **脱离终端**：`setsid` + `nohup` 起进程，父进程是 1，不挂在启动它的那个
   终端上（`ps -o pid,ppid,sess,cmd` 能看到 PPID=1）。
2. **崩溃自愈**：`start_web.sh --serve` 是个 `while true` 看门狗，
   `app.py` 退出就等 5 秒再拉起来。实测 `pkill` 掉 python，8 秒内自己恢复。
3. **别让空间休眠**：CloudStudio 空间长时间没活动会休眠，进程跟着冻住。
   在 <https://cloudstudio.net/settings/tokens/new> 建一个访问令牌（要勾权限），
   写进 `~/.cs_token`，再 `./webctl.sh restart`，脚本会自动用 `/workspace/nosleep`
   包一层打心跳。没配令牌也能跑，只是空间休眠后得手动回来重启。

**公网地址**（CloudStudio 的端口转发，本机连外网都不用管防火墙）：

```
https://894a6547050c42f48c0a4e475294176c--5001.ap-shanghai2.cloudstudio.club
```

格式是 `https://{spacekey}--{端口}.{region}.{host}`，spacekey 记在

## 4.5 扩库到 200 本以上

```bash
python expand.py                      # 7 分类各 18 本 + 起点 75 本，最后回填封面
python expand.py --per-category 25     # 每个分类多采点
python expand.py --no-backfill         # 跳过封面回填（快很多）

# 慢（全程 1~3 秒延时，半小时量级），建议后台跑：
nohup python expand.py > logs/expand.out 2>&1 &
```

三步：公开榜单页凑数量 → 起点榜单拿自带封面的书 → 按书名回起点回填封面。
幂等，重跑只会更新不会堆积。**起点这条路上限约 75 本**：rank 页的 `catId`/`gender`
是前端过滤参数，服务端返回的都是同一份榜单（实测枚举 50 个组合只有 33 本），
所以数量靠公开榜单页，封面靠回填。

封面拿不到的书，前端用"书名首字 + 稳定色相"生成占位封面，不影响卡片展示。

## 5. 爬虫注意事项（别跳过这节）

- **限速。** 每次请求之间随机睡 1~3 秒（`config.CRAWL_MIN_DELAY/MAX_DELAY`），
  单页超时 20 秒。这是礼貌，也是别把 IP 搞封的保命手段。批量采集时尤其别调小。
- **看 robots.txt。** 抓之前先 `robots_allows()` 查一次，按 host 缓存。
  不让抓的站点（实测百度百科、知乎专栏、搜狐都会被拦）**直接跳过并记日志**，
  只退回用 Tavily 给的搜索摘要，不硬闯。
- **失败只记日志，不崩。** 任何一条 URL 挂了，往 `logs/failed_urls.log`
  记一行 `时间 | URL | 原因`，继续跑下一条。
- **只采元数据。** 书名、作者、分类、简介、评分、封面、来源链接这些出版信息，
  **不抓正文**。小说正文受版权保护，抓下来再分发是另一回事。
  `selftest.py` 里有断言卡这条底线：起点记录里不允许出现 `content` / `chapter` 字段。
- **起点有反爬，别硬闯。** `www.qidian.com` 和 `book.qidian.com` 直连一律 202（风控页），
  只有移动端 `m.qidian.com` 返回 200。**这只是绕开风控，不是绕开授权**：
  拿的仍然只是公开元数据。抓不到就记日志跳过，绝不重试轰炸。
- **过滤噪声。** `crawler.clean_text()` 逐句砍掉广告、备案号、举报电话、
  百科界面词和表格行；作者名有停用词表（踩过把"正序浏览""简介"当作者名的坑）。
- **采集结果有噪声是正常的。** 榜单页是人工写的，作者可能填成评论人、
  简介可能只有一句话。简介不足 40 字时系统会给一句兜底
  （"《XX》是金庸创作的武侠类小说。"），保证语义检索有东西可比。
- **换 embedding 模型要重建索引。** `python store.py` 会重建。
  本地哈希向量和 `BAAI/bge-m3` 都是 1024 维，光比维度看不出区别，
  所以代码连模型名一起比（这个坑在 `novel_search_agent` 里踩过）。

## 6.5 静态只读站：工作区停了网址还在

**为什么要有这一套**：CloudStudio 的「Jupyter 开发环境」就是工作区容器本身，
停止它 = 停容器，里面所有进程一起没，公网域名也跟着失效。`start_web.sh`
只能保证"关掉终端不死"，保证不了"停掉环境还在"。要真正脱离工作区，
只能把网站发布成**不依赖后端的纯静态站**。

### 导出数据

```bash
python3 export_static.py
```

产出 `static_site/data/` 下两个文件：

| 文件 | 大小 | 用途 |
|---|---|---|
| `meta.json` | 1.3 KB | 分类统计 + 生成时间。小，先加载，侧栏不用等大文件 |
| `novels.json` | 5.5 MB（gzip 后 1.9 MB） | 全部小说的精简字段快照 |

**这是快照不是镜像**：之后再采新书，静态站不会跟着变，要重跑一次脚本再发布。

### 发布

先打包（**关键：zip 的根目录必须直接是 `index.html`**，不能多套一层 `static_site/`，
否则线上首页 404）：

```bash
cd static_site && zip -r ../novel-site.zip .    # 或 python3 -m zipfile -c ../novel-site.zip .
```

把 zip 上传到静态托管即可。国内可用的：

| 平台 | 费用 | 备注 |
|---|---|---|
| 腾讯云 EdgeOne Pages | 免费 | 国内节点，用平台送的二级域名**不用备案** |
| 腾讯云 CloudBase 静态网站托管 | 按量（有免费额度） | 同上 |
| GitHub Pages | 免费 | 国内访问不稳，演示慎用 |

绑自己的域名走国内节点需要 ICP 备案，实训演示没必要，用平台送的二级域名就行。

**EdgeOne Pages（现名 Makers）上传步骤**：登录
[EO 控制台](https://console.cloud.tencent.com/edgeone) → 顶部切到 **Makers** →
创建项目 → 选**直接上传** → 填项目名（5-50 字符，只能小写字母/数字/连字符）
→ 加速区域选「中国内地」→ 把 zip 拖进上传区 → **开始部署** →
部署完成后在「项目概览」右上角点**预览**拿链接。

几个限制（官方 doc 1552/127371）：项目最多 20000 个文件、单文件最大 25MB。
本站点 4 个文件、最大 5.5MB，都在范围内。

> 选了「直接上传」之后这个项目**不能改成 Git 集成**——想 push 自动部署得另建一个
> 用「导入 Git 仓库」的项目。

本地预览：`cd static_site && python3 -m http.server 5002`，开 http://127.0.0.1:5002

### 静态版少了什么

| 功能 | 静态版 | 原因 |
|---|---|---|
| 分类浏览 / 全部列表 / 排序 / 分页 / 详情 | ✅ 一样 | 数据全在浏览器里 |
| 关键词检索（书名·作者·简介） | ✅ 一样 | 已与后端 `count_matches` 逐条对过，8/8 一致 |
| 智能匹配（说人话搜） | ⚠️ 规则版 | 用 `intent.py` 的**规则降级路径**，没有 LLM；整句搜不到时退到字面片段 |
| 语义检索 | ❌ 没有 | 要 embedding 模型 + 33MB FAISS 索引，浏览器跑不了 |
| 在线采集入库 | ❌ 没有 | 静态站没有后端；而且把采集按钮挂在公开页面上，谁都能让你的服务器去爬起点 |

**静态版不改动工作区任何东西**，`app.py` / `novel.db` / FAISS 全在原地，
5001 端口那套完整功能照常用。两套并存：静态站负责"随时能打开"，
工作区负责"开发和数据更新"。

### 检索规则的一致性怎么保证的

`static_site/app.js` 里的每个检索函数都对着后端实现写，并在注释里标了出处：

| 前端 | 后端 |
|---|---|
| `splitKeyword` | `store.split_keyword` |
| `matchRows` | `store._match_where` |
| `sortRows` | `store.keyword_query` 的 ORDER BY（NULL 排最后） |
| `parseSmart` | `intent.parse_intent_rule` |
| `pickKeyword` | `intent._pick_keyword` |

改动任意一边的匹配规则，两边都要跟着改。
